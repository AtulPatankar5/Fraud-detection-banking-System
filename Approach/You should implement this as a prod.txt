We will implement:

| Token         | Purpose                   | Example lifetime |
| ------------- | ------------------------- | ---------------- |
| Access token  | Authorize API requests    | 15 minutes       |
| Refresh token | Obtain a new access token | 7 days           |

These are example lifetimes, not mandatory values.

Implementation flow:

1. User logs in.
2. Backend validates credentials.
3. Generate access token.
4. Generate refresh token.
5. Store a hashed refresh token or token-family record.
6. Client sends access token with API requests.
7. When access token expires, client uses refresh token.
8. Backend validates it and rotates the refresh token.
9. Logout revokes the refresh token.

Important: We will implement refresh-token rotation, reuse detection and revocation.

### Phase 4: Password hashing

Use BCrypt through Spring Security.

```
@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

Registration:

```
String encodedPassword =
        passwordEncoder.encode(request.getPassword());
```

Login:

```
boolean valid =
        passwordEncoder.matches(
            request.getPassword(),
            user.getPassword()
        );
```

Important distinction: Passwords should be hashed, not reversibly encrypted. BCrypt is a one-way password-hashing algorithm.

### Phase 7: Payload hashing and integrity

This needs special attention.

We should distinguish three concepts:

| Concept           | Purpose                                              |
| ----------------- | ---------------------------------------------------- |
| Hashing           | Create a one-way digest of data                      |
| HMAC              | Verify integrity and authenticity using a secret key |
| Digital signature | Verify integrity and the identity of the signer      |

For example, if a payment request contains:

```
{
  "transactionId": "TXN101",
  "amount": 1500.50,
  "accountNumber": "123456789"
}
```

We can use HMAC-SHA256 to authenticate the request payload between trusted systems.

We should also add:

- Timestamp validation
- Nonce or idempotency key
- Replay attack prevention
- Canonical JSON serialization

A plain SHA-256 hash alone does not prove who created the payload.

## 3. Failure scenarios we must cover

This is especially important for a fraud detection project. We should test failure behavior, not just successful requests.

| Scenario                  | Expected behavior                                                 |
| ------------------------- | ----------------------------------------------------------------- |
| Invalid password          | `401 UNAUTHORIZED`                                                |
| Expired access token      | `401 UNAUTHORIZED`                                                |
| Invalid refresh token     | Reject and revoke token family where appropriate                  |
| Account not found         | `404 NOT FOUND`                                                   |
| Insufficient balance      | `422 UNPROCESSABLE ENTITY`                                        |
| Invalid OTP               | Increment attempts and reject                                     |
| OTP expired               | Reject and initiate the defined recovery flow                     |
| OTP attempts exceeded     | Temporarily block verification                                    |
| Fraud detected            | Flag or hold transaction according to business rules              |
| Redis unavailable         | Apply a defined fail-closed or fail-open security policy          |
| Kafka unavailable         | Avoid losing committed business events; use retry/outbox strategy |
| Payment failed            | Mark payment failed and reconcile status                          |
| Duplicate payment webhook | Process idempotently                                              |
| Database unavailable      | Return controlled `503 SERVICE UNAVAILABLE`                       |

For fund transfers, we will also test partial failures: sender debited but receiver not credited, duplicate transfer requests, timeout after successful processing, and refund failures. These require idempotency and Saga compensation.
